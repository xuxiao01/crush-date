# 工程问题复盘

根据本次对话、代码变更、终端输出、页面现象和用户描述，创建一篇面向个人学习的工程问题复盘。不要把它写成普通开发说明或最终代码文档。

## 工作流程

1. 收集与问题直接相关的证据：用户描述、当前对话、代码改动、日志、报错和运行结果。必要时检查关联代码或配置。
2. 先判断信息是否足以确认问题背景、现象、复现条件和原因。证据不足时，在对应位置标注“待补充：需要结合具体代码或运行现象进一步确认”，不要编造。
3. 确认输出目录为 `docs/engineering-notes/bug-review/`；目录不存在时创建。
4. 读取该目录已有文件名，使用下一个三位序号；目录为空时从 `001` 开始。文件名格式为 `序号-问题名称复盘.md`，名称简洁且控制在约 20 个中文字符以内。
5. 实际写入 Markdown 文档，并在完成后报告文件路径、核心主题、最值得记住的 3 个坑点，以及建议补充的 1–3 个知识点。

## 文档要求

用中文、个人学习复盘的口吻，重点解释错误理解、反复修改暴露的问题、工程根因和避免方式。仅选择与本次问题有关的分析方向，例如状态流转、组件职责、CSS 约束、接口类型、路由、异步状态、环境与部署配置、缓存或构建产物。

文档必须按以下结构编写：

```markdown
# <问题名称>问题复盘

## 1. 问题背景
## 2. 现象描述
## 3. 如何复现
## 4. 错误尝试
## 5. 核心原因
## 6. 最终解决方案
## 7. 关键代码 / 配置片段
## 8. 以后如何避免
## 9. 下次遇到类似问题怎么排查
## 10. 这次需要补的知识点
## 11. 一句话总结
```

在“以后如何避免”中给出针对本次问题的 checklist；在“下次遇到类似问题怎么排查”中给出可执行的排查顺序。关键代码或配置只摘录必要片段，并说明其作用与注意点。若问题不是代码问题，可改为保留关键配置、构建或部署信息。
