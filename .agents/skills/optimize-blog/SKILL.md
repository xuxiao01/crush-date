# 优化技术博客

## 遵守内容边界

- 完整阅读原文后再修改。
- 先用一两句话概括文章要表达的主题与核心内容。
- 以原文内容为主体，不擅自增加新观点、新事实或扩展话题。
- 可以合并重复内容、补足必要的过渡语，但不得改变原意。
- 发现疑似事实错误、内容矛盾或缺失核心结构时，单独向用户提出，不直接替用户补写或更改结论。
- 除非用户明确要求事实核验，否则只优化文章，不把资料检索结果混入正文。

## 保护原文件

- 永远不要覆盖或改写原文件。
- 在用户指定的 Skill 或输出目录中新建优化稿。
- 默认命名为 `<原文件名>-优化稿-v1.md`；继续迭代时递增版本号。
- 同一轮只修改用户已确认的范围，保留其他内容。

## 优化标题结构

1. 检查大标题是否准确概括主题，是否包含读者最关心的关键词。
2. 整篇只保留一个一级标题 `#`。
3. 二级标题使用中文章节编号，如 `一、`、`二、`、`三、`。
4. 三级标题使用阿拉伯数字编号，如 `1.`、`2.`、`3.`。
5. 四级标题优先使用有语义的阶段或步骤名称，如 `第一阶段：收集摘要`，不强制使用 `1.1.1`。
6. 保证同一级标题的编号形式、语义粒度与表达方式一致。
7. 避免标题级别跳跃，以及用多个一级标题代替章节层级。
8. 根据阅读顺序重排现有段落；只移动内容，不借机扩写。
9. 如果文章缺少必要的总结或关键承接章节，先把它列为“结构建议”，等待用户确认后再新增。

标题结构示例：

```text
# 文章标题
## 一、核心主题
### 1. 第一个子主题
### 2. 第二个子主题
#### 第一阶段：准备
#### 第二阶段：执行
## 二、另一个核心主题
```

## 生成 GEO 速览区

- 在一级标题下方、常规正文之前固定加入“本文速览”区域。
- 从原文提炼速览内容，不增加原文没有覆盖的知识或承诺。
- 依次包含以下字段：`一句话总结`、`适合人群`、`核心问题`、`你将学会`、`相关关键词`。
- “一句话总结”用一段话概括文章解决的问题和读者收益。
- “适合人群”明确文章面向的读者与阅读场景。
- “核心问题”列出 3～5 个文章实际回答的问题。
- “你将学会”列出 3～5 个可验证的阅读收获。
- “相关关键词”列出 6～12 个与正文高度相关的关键词，使用中文顿号分隔。
- 整个 GEO 速览区只使用纯 Markdown，不使用 `<table>`、`<font>`、`<br>` 或其他 HTML 标签包裹。
- 使用加粗文本标记“本文速览”和各字段名称；“核心问题”与“你将学会”使用 Markdown 列表。
- 不把“本文速览”设置为 Markdown 标题，避免干扰文章目录。
- 在“相关关键词”之后加入一条 `---` 分隔线，然后直接进入第一个二级标题。
- 删除 GEO 后与“一句话总结”重复的引用、导语或“本文将介绍”等概述，不要重复总结文章内容。

GEO 速览区格式：

```markdown
**本文速览**

**一句话总结：**

内容……

**适合人群：**

内容……

**核心问题：**

- 问题一？
- 问题二？

**你将学会：**

- 收获一；
- 收获二。

**相关关键词：**

关键词一、关键词二、关键词三

---

## 一、正文主题
```

## 整理 Markdown 样式

- 将 `[toc]` 固定放在每篇优化稿的第一行，下一行留空后再写一级标题；不得遗漏或移动到文章中间。
- 面向 CSDN 与掘金发布时，以用户指定的 `[toc]` 和标准 Markdown 为基础。
- 在标题、段落、列表、引用和代码块之间保留空行。
- 路径、文件名、命令和配置字段使用行内代码。
- 每个围栏代码块的起始围栏必须填写语言标识，禁止使用裸起始围栏 ` ``` `；结束围栏必须保持为单独的 ` ``` `，不得填写语言。
- 为每个代码块标注与内容匹配的语言以启用语法高亮：目录树、日志、输出结果和纯文本流程使用 `text`，可渲染图表使用 `mermaid`，JavaScript 使用 `javascript`，TypeScript 使用 `typescript`，JSX 使用 `jsx`，TSX 使用 `tsx`，Vue 单文件组件使用 `vue`，HTML 使用 `html`，CSS 使用 `css`，JSON 使用 `json`，YAML 使用 `yaml`，Shell 命令使用 `bash`，Python 使用 `python`，Java 使用 `java`，SQL 使用 `sql`，TOML 使用 `toml`，Codex Rules 使用 `starlark`。
- 无法确定具体语言或内容本身没有语法高亮规则时使用 `text`，不要为了产生颜色而填写错误的语言。
- 用引用块突出少量定义或关键结论，不连续堆叠引用块。
- 列表句式和标点保持一致，删除无意义的空行与重复提示词。
- 在关键提醒、路径差异、易错点或核心规则前使用 `<strong><font color="#2563EB">注意</font></strong>：`、`提示` 或 `重点`，只为标签着色并加粗，说明文字保持正常颜色。
- 每篇文章通常使用 3～5 个彩色提示标签，避免提示过多而失去重点。
- 统一标签语义：`提示` 表示补充信息，`注意` 表示易错点，`重点` 表示需要记住的核心结论，`结论` 表示全文收束。
- 正文中间仍使用普通 Markdown；不要把所有段落都放进表格或设置颜色。
- 除用户指定的提示框样式外，不依赖复杂 HTML、内联 CSS 或其他平台专属组件。
- 不主动添加 emoji、装饰性分隔线或夸张的小标题。

## 克制使用 Mermaid 图表

- 只在流程、职责关系、时序、层级或分支用文字难以一眼看懂时使用 Mermaid。
- 一篇文章通常使用 1～2 张 Mermaid 图，不为装饰而画图。
- 优先使用基础 `flowchart` 语法、带引号的节点文本和简单箭头，避免依赖实验性语法、复杂初始化配置或大量图形。
- Mermaid 图中的文字必须来自正文，不增加正文没有讲过的概念。
- 图表必须放在对应解释附近：流程图放在流程说明之后、分步详解之前；关系图放在职责差异说明之后。
- 图表不能替代正文。保留可被搜索引擎、AI 和不支持 Mermaid 的平台读取的文字说明。
- 不在 Mermaid 图旁边重复一份内容完全相同的 ASCII/纯文本流程图；改用简短段落或分步说明保留语义。
- 目录树继续使用 `text` 代码块，不转换成 Mermaid。
- 可以使用少量 `classDef` 统一颜色：普通节点使用蓝色系 `#2563EB` / `#EFF6FF`，结果或范围节点使用绿色系 `#16A34A` / `#F0FDF4`。
- 发布前在目标平台预览 Mermaid。若平台无法渲染，使用同一份 Mermaid 源码导出 SVG 或 PNG，正文仍保留必要的文字解释。

基础流程图示例：

```mermaid
flowchart LR
    A["步骤一"] --> B["步骤二"] --> C["完成"]

    classDef primary fill:#EFF6FF,stroke:#2563EB,color:#0F172A;
    classDef success fill:#F0FDF4,stroke:#16A34A,color:#0F172A;
    class A,B primary;
    class C success;
```

## 使用正文与结尾配色

### 正文提示：蓝色系

- 文字颜色使用 `#2563EB`。
- 背景颜色使用 `#EFF6FF`。
- 用于正文中的开篇说明、重要提醒、路径差异和核心范围界定。
- 不得用于 GEO“本文速览”区域。

```html
<strong><font color="#2563EB">注意</font></strong>：

<table>
  <tr>
    <td bgcolor="#EFF6FF">
      第一条需要注意的内容。<br>
      第二条需要注意的内容。
    </td>
  </tr>
</table>
```

### 结尾与结论：绿色系

- 文字颜色使用 `#16A34A`。
- 背景颜色使用 `#F0FDF4`。
- 用于结论、最终记忆点和全文收束。

```html
<strong><font color="#16A34A">结论</font></strong>：

<table>
  <tr>
    <td bgcolor="#F0FDF4">
      用一小段话总结全文核心结论。<br>
      不在结论中增加正文没有讲过的新观点。
    </td>
  </tr>
</table>
```

## 执行流程

1. 读取原文并概括主题。
2. 列出标题层级与主要结构问题。
3. 提出不超过三项需要用户决策的核心结构建议；没有则直接说明。
4. 从原文生成 GEO 速览区。
5. 新建优化稿，完成已授权的标题重构与样式整理。
6. 判断是否有 1～2 个重要流程或关系确实需要 Mermaid；没有则不添加。
7. 在文章末尾使用绿色系结论框收束全文。
8. 检查 `[toc]`、标题编号、GEO 字段、代码块语言、Mermaid 语法和正文/结尾配色；逐个确认所有代码块的起始围栏都有准确语言，且只有结束围栏为空；确认 GEO 区域不含 HTML 标签，且 GEO 后没有重复导语。
9. 对照原文检查：主题、观点、示例、路径和结论不得遗漏或失真。
10. 告知用户新文件位置，并简述本轮修改范围与待确认问题。
11. 根据用户反馈继续生成下一版本，不覆盖上一版。

## 输出要求

- 优化稿应可直接作为 Markdown 预览和发布。
- 优化稿第一行必须是 `[toc]`。
- 一级标题下方必须包含完整、纯 Markdown 的“本文速览”GEO 区域。
- GEO 区域不得使用 HTML；GEO 后使用单条分隔线并直接进入正文，不重复文章概述。
- 正文提示使用柔和蓝色系，结尾使用柔和绿色系，中间正文以普通 Markdown 为主；彩色标签只为标签文字着色并加粗。
- Mermaid 仅在确有理解价值时使用，并保留对应文字说明。
- 所有围栏代码块的起始围栏必须包含准确的语言标识；纯文本内容使用 `text`。
- 回复应先说明结果，再列出关键调整和待确认项。
- 不用大段解释代替实际优化稿。
